为什么用 NestJS，而不是 Koa/Express？

我选择 NestJS 而不是 Koa 或 Express，核心原因是它更适合中大型、长期演进的系统。

Koa 和 Express 非常灵活，但对项目结构几乎没有约束，随着业务复杂度提升，很容易出现逻辑分散、依赖混乱的问题。

NestJS 通过模块化、依赖注入以及 Controller / Service 的明确分层，在框架层面约束了架构形态，这对多人协作和后期维护非常关键。

同时，像鉴权、日志、异常处理这类横切关注点，NestJS 可以用 Guard、Interceptor 等机制统一处理，业务代码会更干净、也更安全。

所以在需要稳定性、可维护性和扩展性的场景下，我会优先选择 NestJS；而在轻量服务中，Koa 或 Express 依然是合适的选择。

NestJS 的主要成本在于学习曲线和框架抽象层级相对较高。

对小项目来说，模块、依赖注入这些机制一开始会显得偏重，开发速度可能不如直接用 Express。

我的做法是：
在项目早期就明确规模预期，如果是工具型或短生命周期服务，我不会强行上 NestJS；
如果是核心业务系统，我会通过约定模块粒度、避免过度拆分，控制复杂度，让框架为业务服务，而不是反过来。

NestJS典型后端服务的分层

NestJS 的请求执行顺序是：Middleware 最先介入，随后由 Guard 决定是否执行，Interceptor 包裹整个调用过程，Pipe 负责参数校验，Controller 和 Service 执行业务逻辑，Interceptor 在返回阶段处理结果，异常则由 Exception Filter 统一兜底。

执行顺序：中间件 → 路由匹配 → 守卫 → 管道 → 控制器 → 服务 → 拦截器 → 异常过滤器

一个请求进入 NestJS 后，先经过底层的 HTTP 适配器和中间件做通用预处理，然后完成路由匹配。

在真正执行控制器方法前，会依次经过 Guard 做鉴权和权限判断，Pipe 做参数校验与类型转换。

通过后进入 Controller，再调用 Service 执行业务逻辑。

整个执行过程会被 Interceptor 包裹，用于日志、性能统计或统一响应结构；如果抛出异常，则由 Exception Filter 统一处理并返回客户端。

NestJS 通过把请求生命周期拆解为多个可插拔的阶段，把复杂系统中容易失控的问题前置解决，这也是它更适合中大型系统的原因。

如何防止 Controller 里业务逻辑失控

在 NestJS 中，通过Controller 极薄、业务逻辑全在 Service、横切关注点通过 Guard/Pipe/Interceptor 管理、模块化组织，可以保证 Controller 不会成为业务逻辑的黑洞，从而系统可维护、安全且易于测试。

Node.js 并发模型

单线程事件循环
Node.js 使用 单线程事件循环 + 异步非阻塞 I/O 模型来处理高并发，通过事件队列和 libuv 线程池实现 I/O 并行，但 CPU 密集型任务仍然会阻塞事件循环。
Node.js 只有一个主线程（执行 JS 代码）
事件循环持续监听事件队列（Timers、I/O 回调、Microtask 等）
微任务队列（Promises、process.nextTick）
宏任务队列（setTimeout/setImmediate、I/O 回调）
Node.js 并发靠单线程事件循环处理异步 I/O，高并发不是靠多线程，而是靠非阻塞 I/O、事件队列和 libuv 线程池；CPU 密集型任务需要 Worker Threads 或多进程，否则会阻塞事件循环。

非阻塞 I/O
CPU 密集型任务的处理方式（子线程、独立服务）

数据库慢查询
数据库慢查询不能只靠加索引解决，而要通过慢查询日志定位问题 SQL，结合执行计划分析索引、SQL 写法、数据量和锁竞争，从 SQL、数据模型、缓存到架构层进行分层治理，避免把数据库当成计算引擎。
SQL：只查必要字段；设计覆盖索引；调整联合索引顺序；拆复杂sql为多次简单查询；分页查询；
数据模型：冷热数据拆表；历史数据归档；合理反范式；读写分离；
缓存：Redis 缓存热点数据；接口级缓存；防止缓存击穿；
架构：分库分表；引入es；走异步；
慢查询不一定是 SQL 本身慢，也可能是并发高、锁竞争或连接池耗尽。
索引并不是越多越好，当索引选择性低、SQL 不匹配索引、或者更新频繁时，索引会增加额外维护和回表成本，反而让查询变慢。
索引加了反而慢，通常是因为索引选择性低、回表成本高、写入维护代价大或优化器选错索引；联合索引设计要遵循最左前缀原则，把高区分度、等值查询字段放前面，范围查询放最后，并尽量设计成覆盖索引。
真正的索引设计是基于查询模式设计索引，而不是基于表结构设计索引。

热点数据
缓存穿透 / 击穿 / 雪崩
连接池配置（DB / Redis）
连接池过大会放大慢 SQL
连接池耗尽比 SQL 慢更可怕
数据库是共享资源（多服务实例要整体评估连接数）
MySQL 连接池大小由数据库 max_connections、单连接资源消耗、SQL 执行时间和业务并发共同决定；连接池不是越大越好，通常几十到一两百已经是上限，超过这个规模就应该通过 SQL 优化、缓存和架构拆分来解决，而不是继续堆连接。

数据库建模 & 优化

表设计原则（是否反范式、冗余字段的取舍）
索引设计（联合索引顺序、覆盖索引）
高选择性字段在前；等值查询在前，范围查询在后

事务与一致性
分库分表的触发条件

数据库建模应以业务查询模式为核心，默认采用范式保证一致性，在高频读和性能瓶颈场景下通过可控的反范式和冗余字段优化读性能；索引设计遵循最左前缀和覆盖索引原则；事务需要在一致性与并发之间权衡；分库分表只有在单表规模和并发成为瓶颈时才引入，以避免系统复杂度过早失控。

redis和MySQL 数据不一致怎么办

双写策略、延迟双删、以数据库为准、缓存只作为加速层

更新 DB + 删除缓存，是工程上最稳妥的一致性方案。
缓存删除失败怎么办？
重试（本地重试 / MQ 重试）
延迟双删
依赖 TTL 自动过期（兜底）

Redis 和 MySQL 在工程上采用最终一致性，数据库是唯一事实源；主流方案是 Cache Aside 模式，写操作先更新数据库再删除缓存，读操作缓存未命中再回源数据库并回填缓存，通过 TTL、重试或延迟双删兜底，避免并发场景下的数据不一致。

Node 系统的安全如何保证？你做过哪些安全加固？

接口安全：
接口鉴权（JWT / OAuth2 / Session）
权限控制（RBAC）
防重放、防刷接口
参数校验（Pipe + class-validator）

Node 系统安全不是单点技术，而是从入口、应用、数据、运行时到运维的纵深防御；通过统一鉴权、权限控制、参数校验、资源隔离和运行时监控，把攻击成本提高到远高于系统价值。

常见安全问题
SQL 注入（ORM + 参数化）
XSS
CSRF
文件上传安全
接口签名

XSS 是把恶意脚本注入页面在浏览器执行，核心防御是安全输出和 CSP；CSRF 是利用浏览器自动携带身份发起跨站请求，核心防御是 CSRF Token、SameSite Cookie 或使用 Header 中的 Token 鉴权。两者攻击点不同，防御手段也完全不同。

如何做接口限流？在网关还是服务层？

接口限流应在“入口保护”和“业务保护”两个层面联合设计。网关适合全局粗粒度限流，减轻后端压力；服务层适合业务粒度限流，如用户、账号、接口维度。常用算法包括固定窗口、滑动窗口、令牌桶和漏桶，结合 Redis 做分布式计数，并配合降级策略和监控告警，保证高并发下系统可用性和用户体验

你如何保证接口的幂等性？

保证接口幂等性核心是让同一请求重复执行不会改变结果，常用方法包括：业务逻辑层幂等判断、唯一索引约束、请求唯一标识（idempotency key） + 缓存记录、事务控制以及 MQ 消费幂等策略。幂等性不仅防止重复请求，也保证分布式系统下的最终一致性和可靠性。
